GUARD

GPU-native, unsupervised drift and anomaly monitoring for PyTorch inference.

Eric Xu·2026

Python·CUDA·Apache-2.0·498 tests

GitHub Design doc

00Abstract

GUARD watches a serving model for distribution shift without labels and without moving outputs off the GPU. Detector kernels run on a second, low-priority CUDA stream and use whatever SM capacity inference leaves idle. A few floats per step reach the host, batched and asynchronous.

Live behaviour is compared against a baseline built offline from known-good data. An online change-point test decides when a departure is real. It attaches to an existing model through a forward hook; the weights are never touched.

01Why

The usual options cost latency, coverage, or time

Models degrade quietly. CPU-side monitoring puts latency on the request path, sampling misses the rare anomalies that matter, and nightly jobs find drift hours late. GUARD computes on every output, on the device the data already lives on. The target is under 2% added p99 latency, verified with Nsight rather than assumed.

Change-point tests, not single-batch thresholds

Each metric stream feeds a Page-Hinkley or CUSUM test with debounce and cooldown. One odd batch doesn't page anyone. Thresholds are per model and get calibrated on your own clean traffic; the runbook has the procedure.

03How it works

The capture copy runs on the inference stream

record_stream isn't enough on its own: CUDA-graph replay, torch.compile in reduce-overhead mode, TensorRT bindings and out= buffers all rewrite the same addresses without the allocator's involvement. Copying in the caller's stream orders the capture against both the forward pass and the next overwrite, for the price of two small device-to-device copies.

A few floats leave the GPU every K steps

A ring slot is reused only after its completion event, which at the default depth finished long ago. Detectors write a few floats to a summary buffer; every K steps those cross to the host through pinned memory, where a CPU thread keeps the windows, runs the change-point tests and exports to Prometheus or OpenTelemetry.

04Failure isolation

Monitoring can never affect serving

  • Every detector runs behind an exception firewall and is disabled after N failures. forward() returns normally.
  • Fixed ring, fixed baselines, fixed pool of pinned buffers. Nothing allocates per request.
  • If export falls behind, summaries are dropped and counted. Inference is never backpressured.
  • Kill switch: GUARD_DISABLED=1, or monitor.disable() at runtime.

05Usage

baseline = load("baselines/vit-b16.guard", expected_model_version="vit-b16@abc123")
monitor  = build_monitor(baseline, Config.from_yaml("guard.yaml"), device="cuda",
                         sink=PrometheusExporter())
model    = GuardModule(model, monitor, embed_layer="encoder.ln", embed_reduce="cls")

logits = model(images)     # same output, same code path, now monitored

Runs in-process with the inference server: no GUARD service, nothing on the request path, one monitor per device. deploy/ has a Dockerfile, Kubernetes manifests, a Grafana dashboard and Alertmanager rules.

06Testing

498 tests; overhead is measured, not assumed

480 tests run on CPU and 18 on hardware. Detectors are checked against NumPy references and property-tested with Hypothesis; a drift-injection test runs clean, gradual, abrupt, recovery and checks that alerts fire and clear. ab_latency.py reports p50, p95 and p99 deltas with GUARD off and on, and fails CI past an SLO. nsight_overlap.sh captures the timeline showing monitor kernels interleaving with inference.

07Limitations

  • Drift is not accuracy loss. Pair it with periodic labelled evaluation.
  • The change-point tests are one-sided; a shift that lowers entropy won't trip the entropy test.
  • Observations during CUDA graph capture are dropped.
  • Not yet: Triton and TorchServe adapters, ADWIN, MMD, multi-GPU validation.
