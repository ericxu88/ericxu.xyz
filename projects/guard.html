GUARD

GPU-native, unsupervised drift and anomaly monitoring for PyTorch inference.

Eric Xu·2026

Python·CUDA·Apache-2.0·498 tests

GitHub Design doc

Abstract

GUARD watches a serving model for distribution shift without labels and without taking outputs off the GPU. Detector kernels run on a separate low-priority CUDA stream, so they execute in whatever SM capacity inference leaves idle, and only a few floats per step cross to the host, batched and asynchronous.

It compares live behaviour against a baseline computed offline from known-good data, and raises an alert when an online change-point test decides the departure is real rather than noise. It attaches to an existing PyTorch model through a forward hook. The weights are never touched.

Why

Models in production degrade quietly. Inputs drift, the mix of predicted classes shifts, individual predictions get less confident, and the serving dashboards look fine the whole time because the model still returns something.

The usual ways of catching this each have a problem. Copying logits and embeddings to the CPU and computing metrics there puts latency and host memory pressure on the request path. Sampling one percent of traffic misses rare anomalies, which are the point. Nightly batch jobs over logged outputs find drift hours late and need every output stored. GUARD computes on every output, in real time, on the device the data already lives on. The design target is a p99 latency increase under 2%, and the repo includes the Nsight harness to verify the overlap instead of assuming it.

What it detects

Shannon entropy: window mean, tail quantile, distance to the baseline histogramConfidence collapse, per-sample OOD

Each metric stream feeds an online change-point test, Page-Hinkley or CUSUM, with debounce and cooldown, so a single odd batch doesn't page anyone. Thresholds are keyed by metric name and have to be calibrated against your own clean traffic; the shipped values are illustrative and the runbook has a procedure for it.

How it works

The part that took the most care is the ring-buffer copy. It's issued on the inference stream, not the monitor stream. record_stream alone isn't enough here: it defers reuse of memory the caching allocator frees, but CUDA-graph replay, torch.compile(mode="reduce-overhead"), TensorRT bindings and pre-allocated out= buffers all rewrite the same addresses every iteration without the allocator being involved. Copying in the caller's stream orders the capture against both the forward pass and the next overwrite. Inference pays two small device-to-device copies for that guarantee.

Slot reuse works the other way around: the inference stream waits on the slot's completion event before overwriting it. At the default ring depth that event has long since completed, so the wait is free in practice.

Detector kernels read from the ring on the low-priority stream, write a few floats into a summary buffer, and every K steps the summaries go to the host asynchronously through a fixed pool of pinned buffers. A CPU aggregation thread keeps the windows, runs the change-point tests, and exports to Prometheus or OpenTelemetry. Baselines are versioned artifacts bound to a model version, checksummed on write and verified on load.

Failure isolation

Monitoring is best-effort and cannot affect serving. That is a rule, not a hope.

  • Every detector call runs behind an exception firewall. A detector that raises is logged once and disabled after N failures; its metric column becomes NaN and the aggregator skips it. forward() returns normally.
  • Fixed ring buffer, fixed baselines, fixed pool of pinned host buffers. Nothing allocates per request.
  • When the export path falls behind, summaries are dropped and counted. Backpressure is never applied to inference.
  • Malformed input (wrong shape, wrong device, oversized batch, active graph capture) is dropped and counted.
  • Kill switch: GUARD_DISABLED=1 in the environment, or monitor.disable() at runtime.

Usage

from guard import Config, GuardModule, PrometheusExporter, build_monitor, load

baseline = load("baselines/vit-b16.guard", expected_model_version="vit-b16@abc123")
config   = Config.from_yaml("guard.yaml")
exporter = PrometheusExporter()

monitor = build_monitor(baseline, config, max_batch=64, device="cuda", sink=exporter)
exporter.start_http_server(config.export.prometheus_port)

model = GuardModule(model, monitor, embed_layer="encoder.ln", embed_reduce="cls")

logits = model(images)     # monitored; same output, same code path

GuardModule registers a forward hook on the named layer to capture the penultimate embedding and reads logits from the return value. If you drive the loop yourself, skip the wrapper and call monitor.observe(logits, embeddings) after forward(). A baseline is built offline from an iterable of (logits, embeddings) batches; calibrate on substantially more samples than the embedding dimension or the reference covariance is ill-conditioned.

GUARD runs in-process with the inference server. There is no GUARD service and nothing of GUARD's on the request path. One monitor per device, metrics per process, so scrape per-pod endpoints. The deploy/ directory has a reference Dockerfile, Kubernetes manifests, a Grafana dashboard and Alertmanager rules.

Testing and benchmarks

480 tests run without a GPU and 18 run on hardware. The stream and event layer degrades to no-ops off CUDA, so slot rotation, drain batching, buffer exhaustion, failure isolation and concurrency are all covered by the CPU suite. One test drives the engine through a recording stand-in for torch.cuda and asserts the ordering contract the memory-safety argument depends on. Detectors are checked against independent NumPy references and property-tested with Hypothesis, and a drift-injection test runs clean, gradual, abrupt, recovery and asserts that alerts both fire and clear.

Overhead depends on how much SM capacity inference leaves idle, so it has to be measured on your model and your hardware. ab_latency.py reports p50, p95 and p99 deltas with GUARD off and on, timed with CUDA events in interleaved A/B blocks, and exits non-zero if the overhead exceeds an SLO, so it can gate CI. saturation.py sweeps batch size to show where the overlap stops being free, and nsight_overlap.sh captures the timeline that confirms monitor kernels interleave with inference rather than serialising after it.

Limitations

  • Drift is not accuracy loss. GUARD detects behavioural change, which usually but not always means degradation. Pair it with periodic labelled evaluation.
  • A stale baseline alarms on legitimate evolution; a too-fresh one masks real drift. Re-baselining is a human-approved workflow, not an automatic one.
  • The change-point tests are one-sided. They catch metrics rising, which is the direction drift moves them. A shift that reduces entropy will not trip the entropy test.
  • Observations during CUDA graph capture are dropped. Per-step hooks can't fire inside a captured graph.
  • Not implemented: Triton and TorchServe adapters, ADWIN, MMD with random Fourier features, multi-GPU validation.
