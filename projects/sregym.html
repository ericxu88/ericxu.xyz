SREGym

A procedurally generated incident-response environment for LLM agents.

Eric Xu·August 2026

Python·Apache-2.0·178 tests·Active

GitHub Environments Hub

Abstract

SREGym tests whether an LLM agent can actually hold an on-call shift. Every episode builds a small but complete production stack on local disk: a FastAPI service, SQLite databases, a git repo with a plausible history, nginx, systemd and cron config, and hours of logs and metrics that agree with each other. A known fault gets injected, the agent gets paged, and a deterministic verifier decides whether it fixed the real root cause without breaking anything else. There is no LLM judge anywhere in the loop.

Worlds are procedural, so seeds are reproducible and they don't repeat: 10 fault templates plus two-fault compositions, three difficulty profiles, and 8 stack identities. It ships with Anthropic and OpenAI-compatible adapters, a scripted reference solver, a sweep runner, and a verifiers taskset published on Prime Intellect's Environments Hub.

What the agent sees

The agent gets the page above, a support note, and a system prompt that covers the host layout, the tools, and what counts as a good resolution. Both prompts are stored in the trajectory. From there it has seven tools and a step budget.

ToolNotes
read_logspaginated, 50 lines max per call, cursors, regex grep, since/until, tail
query_metricsper-minute series: requests by method/path/status, latency, db errors, up, derived error rate
read_filenumbered lines
edit_fileexact-string replace, returns a diff; log files are read-only
run_shellallow-listed: inspection commands, git (no reset, clean or push), read-only sqlite3, curl to 127.0.0.1. Pipes are fine, redirection and substitution are not
restart_servicesystemctl-style; a restart re-reads .env
resolve_incidentterminal; the agent submits a postmortem

During the episode the service is really running as a uvicorn subprocess. Synthetic traffic keeps flowing at about 1.5 requests per second, a collector scrapes /metrics every 10 seconds, and a real cron daemon runs the deployed jobs. The process starts with a clean environment, so a restart is required to pick up config changes. A lot of episodes go wrong right there.

The scripted solver is a solvability oracle, not a benchmark. It scores 1.0 on every seed, and its mask, workaround, noop and sloppy modes exercise the failure cases the verifier has to tell apart.

What gets generated

The world generator seeds a few hundred users and thousands of orders and payments into SQLite, then renders the app source from templates with feature sections, so each of the roughly nine commits in the git history plausibly adds its feature. The history generator drives one simulated request stream into the app log, the nginx logs, the metrics and the database together, which is what makes the evidence agree with itself. It includes noise on purpose: 404s, a slow-query burst, health probes, cron output, old deploys.

<world>/
  .sregym/              control plane: world.json, spec.json (the answer), manifest.json
                        sibling of host/, unreachable by the tools
  host/                 what the agent operates on
    checkout-service/   git repo, ~9 commits over 90 days (name varies per seed)
      .env  checkout/*.py  migrations/  scripts/  data/*.db  logs/
    etc/nginx  etc/systemd  etc/cron.d  var/log/nginx/  metrics/series.jsonl

The answer key lives next to the host root, not inside it, and the tools can't reach it. I tested that against grep -r, globs, .. and absolute paths. Timestamps are real wall-clock UTC, so the live logs continue from the generated history without a seam.

Faults

A template implements inject(world, seed) -> VerificationSpec: three declarative check lists (symptom, root cause, collateral) plus an incident timeline. The verifier only interprets check types, so templates never touch the verifier.

  • env_var_typo. A config deploy typo'd a database env var, either the value or the key name. Key typos silently fall back to a dev default. Fix the line and restart.
  • ledger_divergence. LEDGER_DATABASE_URL points at a stale audit snapshot. Nothing errors; payments land in the wrong file and a freshness metric pages. A full fix restores the URL, restarts, and backfills the diverted payments with the repo's reconcile script. Config plus restart alone scores 0.7.
  • unapplied_migration. A release needs a schema migration nobody ran. In 30% of seeds the migration file was never committed and has to be written. Reverting the release counts as a workaround.
  • cron_write_lock. A backfill job on * * * * * holds the DB write lock for 20 to 40 seconds per run, so checkouts fail in bursts aligned to the minute. There's no deploy to blame. Verification probes for 65 seconds so a restart-only fix gets caught by the next burst.
  • db_file_permissions. The config-management agent chmod'd the data path read-only. Reads work, writes 500. The trail is fleetd.log and ls -la.
  • bad_dependency_pin. A bumped internal package removed an API; the service crash-loops and stays down, with real captured tracebacks and 502s at the edge. Rollback and fix-forward are both accepted. Incoherent mixtures are not.
  • rate_limit_misconfig. The per-user checkout rate limit got set to 1 to 3 per minute ("clamp to 100" says the commit message). Zero 5xx; legitimate retry bursts get 429. Verified with a six-request burst probe.
  • disk_full. A capacity-guardrail deploy set the DB page quota below the database's current size, so every write fails with a genuine "database or disk is full" while df shows plenty of space. Real ENOSPC needs privileged mounts, and a faked error string would be reward-hackable, so the quota produces the real error live.
  • stale_secret. A quarterly rotation also rotated the webhook secret shared with the payment gateway. Settlement webhooks 401 and settlements quietly stop while checkouts keep working. Restore the old secret from git history. Bypassing signature validation in code is caught.
  • truncated_env. deploy-bot died mid-write and left .env truncated on disk; git has the good copy. Everything below the cut falls back to dev defaults, and because LOG_PATH is gone, app.log goes dark at exactly the restart. The missing traceback is the clue. Restoring only the DB lines leaves dev secrets in prod and counts as incomplete.

Composition puts two faults in one world with one page. The vetted pairs are migration+perms (the migration can't apply until the write bit is back), ratelimit+perms, and migration+cron. Checks are member-prefixed so reports show partial progress, but the reward is all or nothing.

Verifier and reward

The verifier is deterministic and runs against the live world at the end of the episode. It asks three questions.

  • symptom_resolved: live probes. Health returns 200, a synthetic checkout returns 201, reads return 200.
  • root_cause_fixed: the specific broken thing is correct again, the app code is unchanged (hardcoding around the problem is not a fix), and nothing was moved to match a typo.
  • no_collateral_damage: file hashes match the manifest minus allowed files, DB rows and schema are intact (additive changes are fine), logs aren't truncated, git history is intact, and no destructive command succeeded. That last one is judged on command structure, never on quoted text.

Reward is 1.0 if all three hold. Otherwise it's 0.3 for the symptom plus 0.7 for the root cause, halved on collateral damage. So a restart-only fix scores 0.0, a hardcoded workaround 0.15, a correct fix where the agent forgot to restart 0.7, and a correct fix plus an unrelated edit 0.5.

Three rubric principles came out of calibrating this: accept every coherent end state, treat the root cause as the narrowest causal object, and when a template fails uniformly across seeds, suspect the rubric before the model.

Budgets are the main difficulty lever for frontier models. On env_var_typo, Sonnet 5 goes 100% at 30 steps, 95% at 12, 65% at 10 and 15% at 8. As the budget shrinks, failures shift from fixed_not_restarted to never_found. Prompt verbosity made no difference. Opus 5 also went 20/20 at 30 steps, at about $0.26 per episode.

bad_dependency_pin's first measurement came back 0/20, every episode scored as a workaround. All twenty had migrated the callers to the new API instead of rolling the pin back. The unanimity was the tell: the model was right and my rubric was too opinionated. The verifier now accepts either coherent end state, rollback or fix-forward, and the re-measure is the 100% row above. The same calibration pass caught two verifier false positives, a regex matching commit-message text and a path matching a git-checkout heuristic. sregym rescore re-judged the saved results without re-running any models.

Composition is the first configuration where difficulty comes from scope rather than time pressure. Of the 14 failures at 20 steps, 8 had fully fixed exactly one of the two faults and 6 had fixed neither. Per pair: ratelimit+perms 5/8, migration+perms 1/4, migration+cron 0/8.

The difficulty profiles set the step budget (30, 20 or 12) and add 0, 2 or 4 seeded red herrings: a decoy config deploy with a deferred restart, a decoy cron entry, a bot scanning for 404s, and an #incidents chatter block with plausible wrong theories. Herrings only add noise, they never remove evidence. On two templates that were 95 to 100% at baseline, standard and hard came out at 60% and 50% for db_file_permissions and 25% for bad_dependency_pin at hard, mostly never_found. The budget does most of that work: Sonnet 5 spends 0.0 to 0.1 calls per episode on the decoys. I expect the herrings matter more for weaker models and for composition.

Stack variation turned out to be difficulty-neutral, which was the goal. Every world draws one of 8 identities from its seed: service name, Python package, database filenames, and API route prefix. The identity is consistent through the git history, logs, metrics labels, live process, tool docs and verifier probes, so there's no single checkout-service playbook to memorize. Paired against the classic identity on 40 seeds the varied worlds scored 57.5% vs 70%, but that gap is run-to-run variance: the 7 seeds that drew the classic identity both times swung from 6/7 to 2/7 on identical worlds, and the varied rate lands on the 200-seed baseline of 58%.

Using it

Needs Python 3.10 or newer, git and sqlite3. No Docker required, though there is a Dockerfile for models you trust less than the tool sandbox.

uv venv --python 3.12 .venv && uv pip install --python .venv/bin/python -e ".[dev]"
source .venv/bin/activate

sregym run --seed 42 --agent scripted                    # offline demo, no API key, ~4s
sregym run --seed 42 --agent anthropic --model claude-opus-5 --max-steps 30
sregym sweep --seeds 1-200 --model claude-sonnet-5 --concurrency 4 --out sweeps/run1
sregym report sweeps/run1
sregym generate --seed 7 --serve --reveal                 # poke at a world by hand

Sweeps run seeds concurrently, resume cleanly, retry infrastructure failures with backoff without counting them as model failures, and run each episode in a subprocess with a hard deadline so a hung API read can't stall the run. The report has the success rate with its interval, a failure taxonomy, per-variant and per-herring breakdowns, and cost.

The Environments Hub package wraps all of this as a native verifiers taskset. Each rollout gets its own MCP tool server that owns a live world and exposes exactly the SREGym toolset; verification runs inside that server while the service is still up.

prime env install ericxu88/sregym-env
validate sregym-env -n 2
eval sregym-env -n 5 -m <model> --env.taskset.difficulty standard

Don't pair the taskset with a shell-bearing harness. A raw shell bypasses the sandbox that the collateral scoring depends on.

Limitations

  • Without Docker, the sandbox is an allow-list plus path confinement, and the collateral checks are the real safety net. Don't point an untrusted agent at a host you care about.
  • nginx and deploy-bot exist as config and logs only; the agent hits the uvicorn upstream directly. Cron and the service are real processes.
  • Metrics are a JSONL store, scraped from the app's real Prometheus-format /metrics endpoint.
  • The business domain is always an e-commerce checkout flow, and table and column names are deliberately not varied. They have low memorization value and a large verifier surface.
